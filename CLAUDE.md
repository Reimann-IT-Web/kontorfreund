# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

Open-Source-CRM und Rechnungsprogramm für Kleinunternehmer in Deutschland. Django-Web-App, Bedienung im Browser, läuft auf Linux, macOS und Windows. Lizenz AGPL-3.0-only (Dual Licensing geplant).

Was gebaut wird, steht ausschließlich in `docs/spec/` (Clean-Room-Spezifikation, nach Phasen gegliedert). Neue Funktionen nur, wenn sie dort beschrieben und freigegeben sind.

Produkt: „Kontorfreund (Kleinunternehmen)“ – Marke `settings.PRODUCT_NAME` („Kontorfreund“, Markenprüfung beim DPMA steht noch aus) plus Edition `settings.PRODUCT_EDITION` („Kleinunternehmen“). Weitere Editionen sollen später auf derselben Codebasis entstehen, nicht als Kopie. Name und Edition im Code nie hart codieren; Templates nutzen `product_name` aus `core.context_processors`.

## Befehle

```sh
uv sync
uv run python manage.py migrate
APP_DEBUG=1 uv run python manage.py runserver
uv run pytest
uv run pytest tests/test_start.py::test_startseite        # einzelner Test
uv run ruff check . && uv run ruff format --check .
uv run python manage.py makemigrations --check --dry-run
```

Installationspaket (Spezifikation D-3): `kontorfreund.py` ist das Startprogramm (Daten im Benutzerordner, `migrate` bei jedem Start – die Sicherung davor entsteht nur, wenn es etwas zu migrieren gibt –, waitress auf 127.0.0.1:8765, Browser auf; mit Argumenten wie manage.py für die zuletzt geöffnete Firma). Der Server läuft als Kindprozess (`--server`); endet er mit `firmen.WECHSELN`, startet das Startprogramm ihn mit der Firma aus `firmen.json` neu. Ein Thread ruft alle `TAKT` Sekunden `erinnern` für jede Firma mit eingeschalteten Benachrichtigungen auf. `--hintergrund` startet ohne Browser mit minimiertem Fenster (Autostart). `packaging/kontorfreund.spec` baut mit PyInstaller (`uv sync --group paket`) den Programmordner `dist/Kontorfreund`; Module, die Django nur über Namen lädt, gehören dort in die Liste (z. B. argon2). `uv run python manage.py selbsttest` bzw. `Kontorfreund selbsttest` prüft Seiten, statische Dateien, Kennwörter, PDF mit eigener Schrift und ZUGFeRD lesen und schreiben, ohne Daten zu hinterlassen. `packaging/windows/kontorfreund.iss` (Inno Setup) baut das Installationsprogramm, nur für den Benutzer, ohne Adminrechte. `.github/workflows/paket.yml` baut auf Tag `v*` für Windows, macOS und Linux, prüft mit Selbsttest, Start und (Windows) Installieren/Deinstallieren und legt das Release mit dem Abschnitt aus `CHANGELOG.md` an. Version steht in `pyproject.toml` und `settings.VERSION` (Test vergleicht beide). Ohne Debug-Modus liefert WhiteNoise die statischen Dateien aus; Fehler mit Status 500 landen in `<DATA_DIR>/fehler.log`.

Die CI (`.github/workflows/ci.yml`) führt genau diese Prüfungen aus, Tests auf allen drei Betriebssystemen, plus `pip-audit`. Ein eigener Job lädt KoSIT-Validator, XRechnung-Prüfregeln und Mustang (feste Versionen und Prüfsummen) und prüft damit XML und PDF der Testrechnungen in `tests/test_validierung.py`; ohne diese Werkzeuge wird der Test übersprungen. Neue Versionen: URL und Prüfsumme in der CI ändern, bei KoSIT auch den Jar-Namen im Test.

## Architektur

- `config/` – Django-Projekt. Betriebswerte über Umgebungsvariablen `APP_*` (`APP_DEBUG`, `APP_SECRET_KEY`, `APP_ALLOWED_HOSTS`, `APP_DATA_DIR`).
- Datenverzeichnis (`APP_DATA_DIR`, Standard `./data`, nicht im Repo): SQLite-Datenbank, Dateiablage und der beim ersten Start erzeugte `secret_key`. Ohne Umgebungsvariablen läuft das Programm als Einzelplatz-Installation.
- `core/` – Übersicht, Einstellungen mit `Firmendaten` (genau ein Datensatz, `Firmendaten.laden()`), Seitenleiste (`core/navigation.py`), Kontextprozessoren (Navigation, Suchindex für Strg+K, Firmendaten auf jeder Seite), Template-Tags `kf` (`{% icon %}`, `|euro`, `|zahl`, `|relativ`) und der Formularfeld-Baustein `core/feld.html`. Umsatzgrenzen der Kleinunternehmer in `core/umsatz.py` (Vorjahr 25.000 €, laufendes Jahr 100.000 €, Warnung ab 80 %): Hinweise auf der Übersicht und unter „Umsatzsteuer“ im Rechnungseditor, nach dem Festschreiben als Meldung; eine Rechnung nach § 19, die über 100.000 € führen würde, lässt `invoicing.views._nach_speichern` nicht festschreiben.
- `contacts/` – Adressen (`Kontakt`: Firma oder Person, Nummer K-0001 fortlaufend, Dublettenprüfung, Archiv statt Löschen). Ort zur PLZ: `contacts/plz.py` liest `contacts/daten/plz.tsv` (PLZ, Gemeinde, Zahl der Straßen; aus OpenPLZ/OpenStreetMap, ODbL – Quellenangabe im Dateikopf und in der README behalten; neu erzeugen mit `werkzeuge/plz_erzeugen.py`), eindeutig ab 90 % der Straßen. `/adressen/orte/?plz=` liefert die Orte; Felder mit `PLZ_ATTRS` (`data-plz`) füllen in `static/js/app.js` das Feld mit `data-ort` aus, nur ohne `data-land` oder bei Deutschland und solange der Ort nicht von Hand geändert wurde.
- `invoicing/` – Rechnungen: Entwurf (frei änderbar) → Festschreiben (`beleg.festschreiben`): vergibt die Nummer (`Rechnung.naechste_nummer`, Jahr zweistellig + vierstelliger Zähler, lückenlos nach den Altbelegen), friert alle Angaben in `Rechnung.beleg` (JSON) ein und legt das PDF unter `<DATA_DIR>/archiv/rechnungen/<jahr>/` ab. PDF/A-3 per Typst (`invoicing/typst/rechnung.typ`, Schriften aus `invoicing/schrift/`, Systemschriften ignoriert), ZUGFeRD-XML (EN 16931) mit drafthorse, GiroCode mit segno, Logo aus `Firmendaten.logo` (Bytes in der DB, nicht eingefroren – das abgelegte PDF ist maßgeblich). Vorschau und Ansicht zeigen die PDF-Seiten als PNG (pypdfium2, `beleg.seitenbilder`), nie per iframe: der PDF-Betrachter mancher Browser bleibt dort schwarz. Danach sperren `save()`/`delete()` jede Änderung außer den Versandfeldern. Korrektur nur per Stornorechnung (`beleg.stornieren`): eine eigene, sofort festgeschriebene Rechnung mit `storno_zu` aufs Original, negativen Mengen (EN 16931 verbietet negative Einzelpreise) und BT-25/26 im XML; „storniert“ wird aus dieser Verknüpfung abgeleitet, das Original bleibt unberührt. Teilbeträge mindert eine Rechnungskorrektur (`beleg.korrektur_anlegen`, `Rechnung.korrektur_zu`, mehrere je Rechnung): ein Entwurf mit den Positionen des Originals in negativer Menge, Empfänger und Steuerfall gesperrt, nur negative Mengen und höchstens bis `Rechnung.korrigierter_betrag`; im XML wie die Stornorechnung mit BT-25/26. Nach einer festgeschriebenen Korrektur ist kein Storno mehr möglich, nur weitere Korrekturen. `Rechnung.kopieren()` legt einen neuen Entwurf mit denselben Angaben an. XRechnung 3.0 (CII) für Adressen mit `Kontakt.xrechnung`: dieselbe XML steckt im PDF (Profil XRECHNUNG) und liegt als maßgebliches Original daneben (`Rechnung.xml_datei`, `xml_sha256`). Die Käuferreferenz (BT-10) kommt von der Rechnung oder aus der Adresse; ist sie eine Leitweg-ID (`contacts.models.ist_leitweg_id`, Prüfziffer MOD 97-10), ist sie zugleich die elektronische Adresse des Käufers (Schema 0204). Zusätzliche Pflichtangaben in `Rechnung._fehlt_fuer_xrechnung`. Versand per SMTP mit den Zugangsdaten aus `Firmendaten` (`versand.py`, hängt `beleg.anhaenge` an, auch für Angebote). Live-Rechnen und Pflichtangaben-Anzeige laufen zusätzlich in `static/js/app.js` (`[data-invoice]`, für Angebote mit `data-beleg="angebot"`); maßgeblich ist die Prüfung auf dem Server (`Rechnung.fehlende_angaben`). Was jede Belegart braucht, liegt einzeln in `invoicing/beleg.py` (`absender_daten`, `empfaenger_daten`, `positionen_daten`, `briefkopf`, `druck_positionen`, `druck_summen`, `setzen`) und `invoicing.models.summen`; die Positionszeile des Editors ist `invoicing/position.html`, der Umschalter Rechnungen/Angebote `invoicing/belegarten.html`.
- `angebote/` – Angebote (Spezifikation B-2): Entwurf → Fertigstellen (`beleg.fertigstellen`): Nummer aus eigenem Nummernkreis (`Angebot.naechste_nummer`, Format wie die Rechnung, nach den Altbelegen der Art Angebot), Angaben eingefroren in `Angebot.beleg`, PDF/A-3 mit derselben Typst-Vorlage ohne ZUGFeRD unter `<DATA_DIR>/archiv/angebote/<jahr>/`. Danach gesperrt wie die Rechnung, änderbar sind nur Versand, Antwort des Kunden (`antwort`, `antwort_am`) und `rechnung`; eine geänderte Fassung ist eine Kopie (`Angebot.kopieren`). Gültigkeit in Tagen (`bindefrist`), „abgelaufen“ und der Stand für die Anzeige (`Angebot.stand`) werden abgeleitet. `beleg.rechnung_erstellen` macht aus dem Angebot einen Rechnungsentwurf mit Empfänger, Steuerfall, Betreff und Positionen, Kopftext mit Bezug aufs Angebot; `Angebot.rechnung` (OneToOne, `SET_NULL` beim Löschen des Entwurfs) verhindert eine zweite Rechnung. Offene Angebote stehen auf der Übersicht.
- `auftraege/` – Auftragsbestätigungen (Spezifikation B-2), Seiten unter `/auftragsbestaetigungen/`, aufgebaut wie `angebote/`: Entwurf → Fertigstellen (`beleg.fertigstellen`, eigener Nummernkreis `Auftragsbestaetigung.naechste_nummer` ohne Altbelege, PDF/A-3 unter `<DATA_DIR>/archiv/auftraege/<jahr>/`), danach gesperrt bis auf Versand und `rechnung`. Optional Ausführung (`leistung_von`/`leistung_bis`), die `beleg.rechnung_erstellen` als Leistungszeitraum in den Rechnungsentwurf übernimmt. `beleg.aus_angebot` macht aus einem Angebot einen Entwurf (`Auftragsbestaetigung.angebot`, OneToOne, vermerkt die Zusage); gibt es ihn, führt „Rechnung erstellen“ am Angebot zur Auftragsbestätigung, und die Zusage lässt sich nicht zurücknehmen. Im Editor `data-beleg="auftrag"`.
- `artikel/` – Artikel und Leistungen (Spezifikation B-1): Nummer A-0001 fortlaufend, Einheit aus `invoicing.beleg.EINHEIT_CODE`, Einzelpreis netto, „inaktiv“ statt Löschen. Der Rechnungseditor bietet aktive Artikel unter „Artikel einfügen“ an (`<details>`-Menü, `static/js/app.js`) und als Auswahl im Feld Bezeichnung (`invoicing/artikel_liste.html`, `<datalist id="artikel-liste">`; übernommen wird nur beim Wechsel zu einem anderen Artikel, gemerkt in `data-artikel-name` der Zeile – nicht `data-artikel`, das sind die Menüknöpfe); die Position übernimmt Bezeichnung, Beschreibung, Einheit und Preis als Kopie ohne Verweis, spätere Preisänderungen berühren bestehende Rechnungen nicht. Einen Steuersatz je Artikel gibt es noch nicht, weil die Rechnung einen Steuersatz für alle Positionen hat.
- `archive/` – Ablage (Spezifikation B-9): Tägliche Prüfung aller abgelegten Dateien in `archive/pruefung.py` (Docstring): `_dateien` zählt jede Datei mit gespeicherter SHA-256 auf (Rechnung samt XML, Angebot, Auftragsbestätigung, Mahnung, Altbeleg, Eingangsrechnung – neue Belegarten mit Datei gehören dort hinein), `pruefen` speichert das Ergebnis als `Pruefung` (Befunde als JSON mit `seit` und `neu`) und schreibt jede neue Abweichung als `Eintrag.Aktion.ABLAGE` ins Protokoll. Angestoßen einmal am Tag nach einer angemeldeten Anfrage (`archive.middleware`, Thread wie die Sicherung) und vom Befehl `erinnern`; `nachrichten.ablage` meldet neue Abweichungen einmal per Telegram. Anzeige: Zähler an „Ablage“ in der Seitenleiste und Hinweis auf der Übersicht (`ablage_befunde` aus `core.context_processors.navigation`), Liste und „Jetzt prüfen“ auf der Seite Ablage. „Originale zurückholen“ (nur Inhaber, `pruefung.zurueckholen` → `backups.sicherung.zurueckholen`) entschlüsselt die Sicherungen von der neuesten an mit dem gespeicherten Schlüssel (andere Kennwörter werden übersprungen), nimmt eine Datei nur bei passender SHA-256 aus `inhalt.json` und Datei, verschiebt die abweichende Fassung nach `<DATA_DIR>/abweichungen/<Zeit>/` und protokolliert `Eintrag.Aktion.ZURUECK`. Dazu die Ablage der aus dem Altprogramm übernommenen Belege (`Altbeleg`, Original-PDFs unverändert unter `<DATA_DIR>/archiv/altbelege/`). Übernahme nur aus den vom Altprogramm erzeugten PDFs, nie aus dessen Datenbank: `uv run python manage.py altdaten_importieren <ordner>` zeigt einen Probelauf, `--ausfuehren` übernimmt. Bereits übernommene Dateien (gleiche SHA-256) werden übersprungen. Adressen werden über Kundennummer und Namen zugeordnet: Das Altprogramm hat Kunden teils neu nummeriert, gleicher Name ergibt deshalb eine Adresse mit der jüngsten Nummer.
- `eingang/` – Empfangene E-Rechnungen (Spezifikation M-7), Seiten unter `/eingangsrechnungen/`. `lesen.einlesen` nimmt XML oder PDF (eingebettete XML per pypdf, bevorzugt `factur-x.xml`), `lesen.auswerten` liest XRechnung/ZUGFeRD in CII und UBL (Rechnung und Gutschrift, Unterpositionen und Drittforderungen der XRechnung-Extension) in ein Wörterbuch für die Anzeige; Codelisten (Rechnungsart, Einheit, Zahlungsart, Steuerkategorie) dort auf Deutsch. XML mit DOCTYPE wird abgelehnt (keine Entitäten), Fehler für den Nutzer als `lesen.Unlesbar`. `Eingangsrechnung.ablegen` legt die Datei unverändert unter `<DATA_DIR>/archiv/eingang/<jahr>/` ab (SHA-256 eindeutig, dieselbe Datei zweimal ergibt `Doppelt`) und speichert nur Kopfdaten für Liste und Suche; die Ansicht liest immer die Originaldatei und prüft vorher die Prüfsumme (`Eingangsrechnung.lesen`). Danach ist nur `kontakt` änderbar, löschen geht nicht (`Aufbewahrt`). Der Lieferant wird beim Hochladen zugeordnet, wenn USt-IdNr. oder Name zu genau einer Adresse passen; sonst per Auswahl oder als neue Adresse der Kategorie Lieferant. Eingebettete Anhänge (BG-24) werden nur heruntergeladen, nie im Browser geöffnet. Die CI lädt die offizielle XRechnung-Testsuite (`XRECHNUNG_TESTSUITE`) und prüft in `tests/test_eingang.py`, dass jede Beispielrechnung auf den Cent aufgeht und angezeigt wird.
- `auswertungen/` – Auswertungen (Spezifikation M-5), Seite `/auswertungen/`: Rechnungsausgangsbuch je Jahr, Quartal oder Monat (`buch.zeitraum`). `buch.zeilen` nimmt festgeschriebene Rechnungen, Stornos und Korrekturen mit Empfänger aus dem eingefrorenen Beleg, Zahlungsstand, bezahltem Betrag (ohne Ausbuchung und Skonto), letztem Zahlungsdatum und offenem Betrag sowie die umsatzwirksamen Altbelege (nur Brutto, Netto/USt/Zahlung leer). `tabelle.py` schreibt beliebige Tabellen (Spalten mit Art text/datum/betrag) als CSV (UTF-8 mit BOM, Semikolon, Dezimalkomma), XLSX (openpyxl) und ODS (selbst geschrieben, mimetype zuerst und unkomprimiert); für weitere Exporte wiederverwenden: `tabelle.antwort` liefert den Download, `tabelle.links(request)` die Links für die angezeigte Liste (Vorlage `auswertungen/herunterladen.html`, so unter Adressen und offenen Posten mit `?format=`). Im CSV bekommt Text mit `= + - @` am Anfang ein Hochkomma, außer er besteht nur aus Ziffern und Rechenzeichen (`HARMLOS`, z. B. Telefonnummern). Seite `/auswertungen/datev/`: DATEV-Export (M-4) als Buchungsstapel nach Formatversion 13 (`datev.py`, 125 Felder, Windows-1252, CR/LF), eine Buchung je festgeschriebenem Beleg über den Bruttobetrag vom Debitor an das Erlöskonto des Steuerfalls, Stornos und Korrekturen im Haben; Altbelege fehlen. Einstellungen im Einzelmodell `Datev` (Berater, Mandant, SKR 03/04, Debitor je Kunde = 10000 + Kontaktnummer oder Sammelkonto, Erlöskonten mit Vorbelegung aus `ERLOESKONTEN`), nur für den Inhaber; ohne Berater- und Mandantennummer gibt es nur die Vorschau.
- Mehrere Firmen (`core/firmen.py`, ohne Django, weil das Startprogramm es vor Django braucht): die erste Firma im Hauptordner (`settings.HAUPTORDNER`), weitere in `<Hauptordner>/firmen/<Nummer>`, jede mit eigener Datenbank, Ablage, `secret_key` und Datensicherung; `firmen.json` merkt sich die offene. `settings.FIRMA` ist die Kennung (leer = erste), davon hängen der Name des Sitzungs-Cookies (`sessionid-<Nummer>`, so bleibt man in jeder Firma angemeldet) und das Präfix der Sicherungsdateien ab (`kontorfreund-firma<Nummer>-…`, `sicherung._name`). Seiten unter `/firmen/` (`core/views.py`): Liste und Öffnen auch ohne Anmeldung (außer im Netzwerk), Anlegen und Entfernen leerer Firmen (ohne Konto) nur für den Inhaber. Öffnen schreibt `firmen.json` und beendet den Server nach der Antwort (`sicherung.beenden`, wartet auf eine laufende Sicherung); die Warteseite fragt `/firmen/offen/` ab, bis die neue Firma läuft. Unter `manage.py runserver` (`settings.NEUSTART` falsch) gilt die Wahl erst beim nächsten Start.
- `benachrichtigungen/` – Benachrichtigungen über einen eigenen Telegram-Bot des Nutzers (kostenlose Bot-API, `telegram.py` mit urllib; keine Bezahldienste wie SMS-Anbieter), Seite `/benachrichtigungen/` nur für den Inhaber. Einzelmodell `Einstellung`: Bot-Schlüssel (im Protokoll verdeckt), `bot_name` aus getMe, `chat` und `code`: Verbunden wird über `t.me/<bot>?start=<code>` (Link und QR-Code), `telegram.chat_finden` sucht per getUpdates die private Nachricht „/start <code>“, so kann sich kein Fremder verbinden. Uhrzeit der Tagesübersicht, Vorlauf für Termine, Empfänger = wer eingerichtet hat. `nachrichten.erinnern`: Tagesübersicht einmal am Tag ab der Uhrzeit (heute fällige Wiedervorlagen des Empfängers und ohne Zuständigen, Zahl der überfälligen, neu überfällige Rechnungen, Eingangsrechnungen fällig in `VORHER` Tagen; ohne Inhalt keine Nachricht) und Termine `vorlauf` Minuten vor einer Wiedervorlage mit Uhrzeit, ohne Namen von Kunden und Lieferanten (kein AVV mit Telegram); `Gemeldet` verhindert Doppeltes, Fehler bleiben in `Einstellung.fehler` und werden in der nächsten Runde wiederholt. Befehl `erinnern` (überspringt Firmen mit ausstehenden Migrationen). `autostart.py` setzt den Start beim Anmelden (HKCU Run, nur im installierten Programm unter Windows; das Deinstallieren entfernt ihn).
- `wiedervorlagen/` – Wiedervorlagen (Spezifikation K-4), Seiten unter `/wiedervorlagen/`: `Wiedervorlage` mit Titel, Fälligkeit, optionaler Uhrzeit, Zuständigem (leer = alle), Adresse und optional Angebot oder Rechnung; erledigt über `erledigt_am`/`erledigt_von`/`ergebnis`. `aendern` verschiebt (morgen, Woche, Monat, immer ab heute) oder erledigt bzw. öffnet direkt aus jeder Liste; Zeilen-Vorlage `wiedervorlagen/zeile.html` für Liste, Übersicht und Verlauf, Rücksprung über das Feld `weiter` (nur interne Adressen). Übersicht: fällige (bis heute) und die der nächsten `DEMNAECHST` Tage, jeweils für den Benutzer und ohne Zuständigen (`offen_fuer`); die Seitenleiste zählt die fälligen. Neu mit Vorbelegung über `?kontakt=`, `?angebot=`, `?rechnung=`, `?titel=`, `?in=<Tage>`.
- `historie/` – Kontakthistorie (Spezifikation K-2), Seite `/adressen/<nr>/verlauf/` (Link „Verlauf und Notizen“ in der Adressliste): Schnellerfassung von `Vorgang` (Notiz, Anruf, E-Mail, Termin mit Zeitpunkt, Betreff, Text, Benutzer), offene Wiedervorlagen der Adresse und die Zeitleiste aus `zeitleiste.punkte`, die Vorgänge, erledigte Wiedervorlagen, Angebote, festgeschriebene Rechnungen, Zahlungen, Mahnungen, Altbelege und Eingangsrechnungen zur Laufzeit zusammenstellt (nichts doppelt gespeichert), filterbar nach Art. Aus jedem Eintrag „Nachfassen“ als vorbelegte Wiedervorlage. Noch offen: Dateien an Einträgen (K-3), Einträge von Ansprechpartnern, Erinnerung per E-Mail.
- `backups/` – Datensicherung (Spezifikation 05, D-2), Logik in `backups/sicherung.py`, Dateiformat im Modul-Docstring. Eine Sicherung ist ein mit AES-256-GCM verschlüsseltes ZIP aus Datenbank-Momentaufnahme (SQLite-Backup-API) und `<DATA_DIR>/archiv`, Schlüssel per scrypt aus dem Kennwort des Nutzers. Ein lesbarer Kopf trägt Datum, Anlass und Anzahlen für die Vorschau. Einstellungen und abgeleiteter Schlüssel liegen in `<DATA_DIR>/datensicherung.json`, nie in der Datenbank. Sicherungen landen in `<DATA_DIR>/sicherung/` und werden in einen zweiten Ordner kopiert, alte werden aufgeräumt. Automatisch: einmal am Tag im Hintergrund nach einer Anfrage (Middleware) und vor jeder Migration der Datenbankdatei (`pre_migrate`). Wiederherstellen sichert erst den aktuellen Stand, spielt die Datenbank per Backup-API ein, tauscht das Archiv und migriert danach.
- `konten/` – Anmeldung (Spezifikation K-5): eigenes Benutzermodell `Benutzer` (`AUTH_USER_MODEL`, Anmeldung per E-Mail, Rolle Inhaber oder Mitarbeiter), Argon2, Kennwortregeln in `konten/kennwort.py`, Sperre nach 5 Fehlversuchen für 15 Minuten (Notfall ohne zweiten Inhaber: Befehl `entsperren <email> [--ohne-zwei-faktor]`), Zwei-Faktor-Anmeldung per TOTP (`konten/totp.py`, RFC 6238 ohne Fremdbibliothek, QR-Code mit segno). Jede Seite verlangt eine Anmeldung (`LoginRequiredMiddleware`); öffentliche Views tragen `@login_not_required`. Ohne Benutzer führt die Anmeldeseite zur Einrichtung des ersten Inhabers. Inhaber-Bereiche (Einstellungen, Benutzer, Datensicherung) schützt `konten.rechte.nur_inhaber` (403), Links darauf zeigen Templates nur bei `user.ist_inhaber`. `settings.NETZWERK` ist wahr, sobald `APP_ALLOWED_HOSTS` mehr als den eigenen Rechner erlaubt; dann verlangt `konten.rechte.zwei_faktor_pflicht` von Inhabern die Zwei-Faktor-Anmeldung. Abmeldung nach `APP_ABMELDEN_NACH_STUNDEN` (Standard 8) ohne Anfrage. Notfall ohne Inhaber-Zugang: `uv run python manage.py changepassword <email>`. Anmeldungen und Fehlversuche schreiben die Views ins Protokoll (`protokoll.erfassen.anmeldung`).
- `zahlungen/` – Offene Posten, Zahlungen und Mahnungen (Spezifikation M-1 bis M-3), Seiten unter `/offene-posten/`. Offener Posten ist jede festgeschriebene Rechnung außer Storno und Korrektur (`Rechnung.ist_posten`); `Rechnung.offen` = `korrigierter_betrag` − Zahlungen − Ausbuchungen, negativ heißt zu viel gezahlt; `Rechnung.zahlstand` leitet bezahlt/teilbezahlt/überfällig ab (diese Properties liegen auf der Rechnung und lesen die Rückverweise `zahlungen`, `mahnungen`). `Zahlung`: `betrag` mindert die Rechnung, `nebenkosten` sind gezahlte Mahnkosten und Zinsen; was beim Buchen über den offenen Betrag geht, verrechnet `views.buchen` zuerst damit (`mahnen.offene_nebenkosten`). Ausbuchen ist eine `Zahlung` der Art `ausbuchung` mit Grund in `notiz`. Mahnstufen (`Mahnstufe`, drei Zeilen, angelegt aus `VORGABEN` per `Mahnstufe.alle()`): Abstand nach Ablauf der vorigen Frist, Frist, Gebühr, Zinsen ja/nein, Text mit den Platzhaltern {nummer}, {datum}, {faellig}. Verzug und Zinsen in `zahlungen/zinsen.py` (Regeln im Docstring: Verzug ab Fristablauf der ersten Mahnung, bei Unternehmen spätestens 30 Tage nach Fälligkeit und Zugang; 5 bzw. 9 Prozentpunkte über `Basiszins`, Satzwechsel und Teilzahlungen tagesgenau, 365 Tage). `mahnen.berechnen` liefert Aufstellung und Hinweise, `mahnen.erstellen` legt das Schreiben als PDF/A-3 mit der Rechnungsvorlage ab (`aufstellung` statt Positionen, GiroCode über den Gesamtbetrag) unter `<DATA_DIR>/archiv/mahnungen/<jahr>/`; danach ist die `Mahnung` gesperrt bis auf den Versand, löschen lässt sich nur die letzte (Datei mit). Eine Mahnung je Stufe und Rechnung. Basiszinssätze ab 2023 kommen per Datenmigration, neue trägt der Inhaber unter „Mahnwesen einstellen“ ein; `Basiszins.veraltet()` warnt nach jedem 1.1./1.7. Rechnungsseite: Inclusion-Tag `{% zahlungen_panel %}` (`zahlungen/templatetags/posten.py`), Liste: Dialog `#zahlung-dialog` aus `static/js/app.js`. Verbraucher ist eine Adresse der Art Person (`Kontakt.ist_verbraucher`). Skonto: `Rechnung.skonto_prozent`/`skonto_tage` (höchstens 10 %, Frist kürzer als das Zahlungsziel, `RechnungForm.clean`), eingefroren als `beleg["skonto"]`, im PDF unter dem Zahlungsziel und im XML als BT-20 `#SKONTO#TAGE=n#PROZENT=n.nn#` (BR-DE-18). Gleicht eine Zahlung in der Frist die Rechnung bis auf höchstens das Skonto aus, bucht `views._skonto` den Rest als `Zahlung` der Art `skonto` (zählt wie eine Ausbuchung nicht als Geldeingang). Der Hinweis nach § 286 Abs. 3 BGB (`Rechnung.verzugshinweis`, `beleg.VERZUGSHINWEIS`) wird nur bei Verbrauchern gedruckt; mit ihm gilt für sie in `zinsen.verzug_ab` dieselbe 30-Tage-Regel wie für Unternehmen. Noch nicht gebaut: Kontakthistorie.
- `protokoll/` – Änderungsprotokoll (Spezifikation K-6), Seite `/protokoll/` nur für Inhaber. Signale an den Modellen in `erfassen.ERFASST` schreiben bei Anlage, Änderung und Löschung einen `Eintrag` mit Feld, altem und neuem Wert als Text (editierbare Felder ohne JSON; Kennwörter als „•••“, `last_login` nie). Neue Modelle mit Geschäftsdaten gehören in diese Liste. Wer es war, liest `eintragen` aus der Anfrage, die `middleware.anfrage_merken` in einer ContextVar hält. Positionen von Rechnung und Angebot protokollieren die Editoren als Ganzes (`positionen_geaendert`), weil sie beim Speichern alle neu entstehen. `Eintrag` lässt sich nur anlegen: `save()` auf Bestehendes, `delete()` und `update()`/`delete()` am QuerySet werfen `Unveraenderbar`. Bewusst ohne Datenbank-Trigger, weil Tests mit `transaction=True` die Datenbank am Ende leeren.
- Tests setzen `DATA_DIR` automatisch auf einen Temp-Ordner (`tests/conftest.py`), damit keine Sicherung den echten Datenordner berührt; die tägliche Prüfung der Ablage (`pruefung.bei_bedarf`) ist dort abgeschaltet. Die Fixture `client` ist dort als Inhaber angemeldet; Tests der Anmeldung nehmen `anonym`.
- Jeder weitere Fachbereich bekommt eine eigene App (z. B. `exports`).
- Oberfläche: Django-Templates (`templates/base.html` + App-Templates, Django-6-Partials), eigenes CSS in `static/css/app.css` mit Design-Tokens, kein JS-Framework. Gestaltungsregeln: `PRODUCT.md`, `.impeccable/surfaces/`.
