# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Projekt

Open-Source-CRM und Rechnungsprogramm für Kleinunternehmer in Deutschland. Django-Web-App, Bedienung im Browser, läuft auf Linux, macOS und Windows. Lizenz AGPL-3.0-only (Dual Licensing geplant).

Was gebaut wird, steht ausschließlich in `docs/spec/` (Clean-Room-Spezifikation, nach Phasen gegliedert). Neue Funktionen nur, wenn sie dort beschrieben und freigegeben sind.

Produkt: „Kontorfreund (Kleinunternehmen)“ – Marke `settings.PRODUCT_NAME` („Kontorfreund“, Markenprüfung beim DPMA steht noch aus) plus Edition `settings.PRODUCT_EDITION` („Kleinunternehmen“). Weitere Editionen sollen später auf derselben Codebasis entstehen, nicht als Kopie. Name und Edition im Code nie hart codieren; Templates nutzen `product_name` aus `core.context_processors`.

## Befehle

```sh
uv sync
uv run python manage.py migrate
APP_DEBUG=1 uv run python manage.py runserver
uv run pytest
uv run pytest tests/test_start.py::test_startseite        # einzelner Test
uv run ruff check . && uv run ruff format --check .
uv run python manage.py makemigrations --check --dry-run
```

Installationspaket (Spezifikation D-3): `kontorfreund.py` ist das Startprogramm (Daten im Benutzerordner, `migrate` bei jedem Start – die Sicherung davor entsteht nur, wenn es etwas zu migrieren gibt –, waitress auf 127.0.0.1:8765, Browser auf; mit Argumenten wie manage.py für die zuletzt geöffnete Firma). Der Server läuft als Kindprozess (`--server`); endet er mit `firmen.WECHSELN`, startet das Startprogramm ihn mit der Firma aus `firmen.json` neu. Ein Thread ruft alle `TAKT` Sekunden `erinnern` für jede Firma mit eingeschalteten Benachrichtigungen auf. `--hintergrund` startet ohne Browser mit minimiertem Fenster (Autostart). Portable Fassung: Liegt `portabel.txt` neben dem Programm (`packaging/windows/portabel.txt`, ZIP aus `paket.yml`), liegen die Daten in `Daten` daneben und der Server auf 8766; das Startprogramm setzt `APP_PORTABEL=1`, daraus `settings.PORTABEL` (eigener Cookie-Name, kein Autostart, eigene Antworten in der Hilfe). `packaging/kontorfreund.spec` baut mit PyInstaller (`uv sync --group paket`) den Programmordner `dist/Kontorfreund`; Module, die Django nur über Namen lädt, gehören dort in die Liste (z. B. argon2). Das Aussehen des Windows-Installers liegt in `packaging/windows`: `kontorfreund.iss` baut im `[Code]`-Teil die Seitenleiste, `texte.isl` hält alle eigenen Texte (nur dort sind Umlaute sicher), `bilder/hintergrund.html` ist die Quelle der Hintergrundbilder. `uv run python manage.py selbsttest` bzw. `Kontorfreund selbsttest` prüft Seiten, statische Dateien, Kennwörter, PDF mit eigener Schrift, ZUGFeRD lesen und schreiben, Tabellen aus Excel und LibreOffice lesen und Sichern mit Wiederherstellen, ohne Daten zu hinterlassen. Für die Datensicherung (Abnahme Phase 4) tauscht er `connections["default"]` gegen eine eigene SQLite-Datei in einem temporären Ordner (dazu `override_settings(DATA_DIR=…)`), migriert sie und ruft `sicherung.sichern`/`wiederherstellen` auf; die Verbindung der Installation bleibt offen und unberührt, auch die Testdatenbank im Arbeitsspeicher. `packaging/windows/kontorfreund.iss` (Inno Setup) baut das Installationsprogramm für alle Benutzer nach `C:\Program Files`, mit Adminrechten. `.github/workflows/paket.yml` baut auf Tag `v*` für Windows, macOS und Linux, prüft mit Selbsttest, Start und (Windows) Installieren/Deinstallieren und legt das Release mit dem Abschnitt aus `CHANGELOG.md` an. Version steht in `pyproject.toml` und `settings.VERSION` (Test vergleicht beide). Ohne Debug-Modus liefert WhiteNoise die statischen Dateien aus; Fehler mit Status 500 landen in `<DATA_DIR>/fehler.log`. Eine frühere Installation aus dem Benutzerordner (bis 0.28, unter HKCU, Setup sucht nur unter HKLM) entfernt das Installationsprogramm nach dem Kopieren (`FruehereErsetzen` in `kontorfreund.iss`): ohne erhöhte Rechte, weil der Pfad aus HKCU kommt, und es trägt den Start beim Anmelden neu ein; `paket.yml` prüft das mit dem echten Paket 0.28.1.

Die CI (`.github/workflows/ci.yml`) führt genau diese Prüfungen aus, Tests auf allen drei Betriebssystemen, plus `pip-audit`. Ein eigener Job lädt KoSIT-Validator, XRechnung-Prüfregeln und Mustang (feste Versionen und Prüfsummen) und prüft damit XML und PDF der Testrechnungen in `tests/test_validierung.py`; ohne diese Werkzeuge wird der Test übersprungen. Neue Versionen: URL und Prüfsumme in der CI ändern, bei KoSIT auch den Jar-Namen im Test.

## Architektur

- `config/` – Django-Projekt. Betriebswerte über Umgebungsvariablen `APP_*` (`APP_DEBUG`, `APP_SECRET_KEY`, `APP_ALLOWED_HOSTS`, `APP_DATA_DIR`).
- Datenverzeichnis (`APP_DATA_DIR`, Standard `./data`, nicht im Repo): SQLite-Datenbank, Dateiablage und der beim ersten Start erzeugte `secret_key`. SQLite läuft mit `transaction_mode: IMMEDIATE` und 20 s Wartezeit, weil Sicherung, Prüfung der Ablage und Erinnerungen aus eigenen Threads schreiben; lange Arbeit (Dateien lesen, Prüfsummen) gehört nie in eine offene Transaktion. Ohne Umgebungsvariablen läuft das Programm als Einzelplatz-Installation.
- `core/` – Übersicht, Einstellungen mit `Firmendaten` (genau ein Datensatz, `Firmendaten.laden()`), Seitenleiste (`core/navigation.py`), Kontextprozessoren (Navigation, Suchindex für Strg+K, Firmendaten auf jeder Seite; der Suchindex nimmt bis 500 Adressen mit Ansprechpartner und Straße, je Belegart die neuesten `BELEGE_IM_INDEX` ohne gesperrte Adressen und die aktiven Artikel, „In allen Adressen suchen“ führt mit dem Begriff in die Adressliste; weil er auf jeder Seite steht, prüfen Tests das Fehlen einer Belegnummer im Kontext, nicht im Seitentext), Template-Tags `kf` (`{% icon %}`, `|euro`, `|zahl`, `|relativ`) und der Formularfeld-Baustein `core/feld.html`. Hilfe unter `/hilfe/`: Themen in `core/hilfe.py` (`THEMEN`, auch im Suchindex), je Thema eine Vorlage `core/hilfe/<slug>.html` auf `core/hilfe/thema.html`, häufige Fragen in `core/hilfe/start.html`; Links ins Programm mit `{% url %}`, Sprünge auf Abschnitte prüft `tests/test_hilfe.py`. Ändert sich eine Beschriftung oder ein Ablauf, gehört die Anleitung mit in dieselbe Änderung. Umsatzgrenzen der Kleinunternehmer in `core/umsatz.py` (Vorjahr 25.000 €, laufendes Jahr 100.000 €, Warnung ab 80 %): Hinweise auf der Übersicht und unter „Umsatzsteuer“ im Rechnungseditor, nach dem Festschreiben als Meldung; eine Rechnung nach § 19, die über 100.000 € führen würde, lässt `invoicing.views._nach_speichern` nicht festschreiben.
- `contacts/` – Adressen (`Kontakt`: Firma oder Person, Nummer K-0001 fortlaufend, änderbar über das Formularfeld `kundennummer` (kein Modellfeld des Formulars, `forms.nummer_lesen`), solange `archive.fristen.belege(kontakt)` leer ist, sonst gesperrt; die Änderung trägt `KontaktForm.save` selbst ins Protokoll ein, Dublettenprüfung, Archiv statt Löschen). Ansprechpartner (K-1): eine Person mit `Kontakt.firma` (Rückverweis `personen`; `save()` leert es bei Firmen, eine Firma mit Ansprechpartnern lässt sich nicht zur Person machen, gelöscht wird nur der Verweis). Die Auswahl im Formular zeigt nur Firmen, die nicht gesperrt und nicht archiviert sind (außer der bisherigen); `/adressen/neu/?firma=<pk>` belegt Person, Firma und Kategorien vor und führt nach dem Speichern zurück zur Firma. Kategorien (K-1): Modell `Kategorie` (Name eindeutig ohne Rücksicht auf Groß- und Kleinschreibung, ohne Komma und Semikolon, höchstens 100), `Kontakt.kategorien` mit mehreren. Kunde, Interessent und Lieferant haben eine `kennung` und lassen sich nur umbenennen; der Code holt sie mit `Kategorie.vorgabe(kennung)`, nie über den Namen (Lieferanten bei Eingangsrechnungen, Kunde für neue Adressen, Altbelege und als Vorgabe des Imports). Das Formular nimmt zusätzlich `neue_kategorie`, `forms.kategorien_protokollieren` vermerkt Änderungen als Ganzes am Kontakt. Seite `/adressen/kategorien/` zum Anlegen, Umbenennen und Löschen; der Import trennt an Komma und Semikolon und legt unbekannte erst bei der Übernahme an. Die Liste filtert den Ort und sortiert in Python statt in SQLite (`views._sortieren`, `_alphabetisch` nach DIN 5007, Umlaute beim Grundbuchstaben; `?sortiert=nr|name|ort`, `-` dreht um, Spaltenköpfe aus `contacts/spaltenkopf.html`), weil SQLite Umlaute hinter Z einordnet und `iexact` nur ASCII vergleicht; der Export übernimmt Filter und Reihenfolge. Die Spalten neben Nummer und Name wählt jeder Benutzer (`views.SPALTEN`, gespeichert in `Benutzer.adressen_spalten`, None heißt `SPALTEN_VORGABE`; nicht im Änderungsprotokoll, weil JSON): Menü `details[data-menue]` in der Filterleiste, dessen Felder per `form`-Attribut zum Formular `contacts:spalten` gehören, Zellen in `contacts/zelle.html`; auf dem Handy fehlt das Menü. Daneben bleibt der eine Ansprechpartner, der mit Vor- und Nachname in der Firma selbst steht und auf Belegen gedruckt wird; `Kontakt.position` gilt für Personen und für ihn. Weitere Anschriften (K-1): Modell `Anschrift` (Art Rechnung/Lieferung/Sonstige, Zusatz, Straße, PLZ, Ort, Land; Rückverweis `anschriften`), die Standardanschrift steht weiter im `Kontakt`. `Kontakt.anschrift_zeilen(anschrift)` setzt die Zusatzzeile anstelle des Ansprechpartners, `anschrift_fuer(art)` liefert die erste ihrer Art. Das Formular schickt `anschrift_id`, `_art`, `_zusatz`, `_strasse`, `_plz`, `_ort`, `_land` (`contacts/anschrift.html`, PLZ und Ort je `[data-plz-bereich]`); `forms.anschriften_lesen` ändert vorhandene über ihre ID, statt sie neu anzulegen, weil Belege auf sie verweisen, und gibt eine entfernte, die auf einem Beleg aus `fristen.belege` steht, mit Meldung zurück; `anschriften_speichern` protokolliert sie als Ganzes am Kontakt. Rechnung, Angebot und Auftragsbestätigung haben `anschrift` (Empfänger, leer = Standardanschrift) und `lieferanschrift` (leer = keine), beide `SET_NULL` und in `KOPIERT`; `invoicing.forms.anschriften_pruefen` verlangt Anschriften des gewählten Empfängers, die Auswahl im Editor ist `invoicing/anschrift_wahl.html` (Optionen aller Empfänger mit `data-kontakt`, `static/js/app.js` filtert und wählt bei einem Wechsel die erste der Art aus `data-vorgabe`). Neue Rechnungen nehmen die Rechnungsanschrift, alle drei die Lieferanschrift vor; `beleg.empfaenger_daten(k, anschrift)` und `lieferanschrift_daten` frieren sie ein, die Typst-Vorlage druckt `lieferanschrift` unter dem Betreff, das XML als `ShipToTradeParty` (unbekanntes Land: kein XML, wie beim Empfänger). Weitere Telefonnummern und E-Mail-Adressen (K-1): Modell `Kontaktweg` (Art, Bezeichnung, Wert; Rückverweis `kontaktwege`), die erste steht weiter in `Kontakt.telefon` bzw. `email`, und diese E-Mail-Adresse gilt für Rechnungen. Das Formular schickt die Zeilen als `weg_art`, `weg_bezeichnung`, `weg_wert` (`contacts/kontaktweg.html`, hinzufügen und entfernen in `static/js/app.js`); `forms.kontaktwege_lesen` prüft sie (höchstens 20, Meldung an der Zeile), `kontaktwege_speichern` ersetzt sie und protokolliert sie als Ganzes am Kontakt wie die Positionen einer Rechnung. Suche, Dublettenprüfung (auch im Import), Export der Liste, Auskunft und Gesamtexport (`telefon-email.csv`) berücksichtigen sie. Datenschutz (Spezifikation D-1) in `contacts/datenschutz.py`, Seite `/adressen/<nr>/datenschutz/` nur für den Inhaber: Auskunft als ZIP (Brief per Typst aus `contacts/typst/auskunft.typ` im Aussehen der Rechnung, `auskunft.json`, Kopien der Belege und Dateien; vermerkt als Aktion `auskunft` im Protokoll; der Selbsttest setzt den Brief). Fristen aus `archive/fristen.py`. Ist keine Frist mehr offen, löscht `loeschen()` die Adresse samt Vorgängen, Dateien, Wiedervorlagen, Entwürfen und abgelaufenen Belegen (`fristen.entfernen`), schwärzt danach deren Protokolleinträge (`protokoll.erfassen.schwaerzen`) und trägt `loeschung` mit Kundennummer ein. Sonst setzt `sperren()` `Kontakt.gesperrt_am` und `archiviert`, löscht Entwürfe und erledigt offene Wiedervorlagen. Gesperrte Adressen fehlen in Listen, Suche, Auswahlfeldern, Dublettenprüfung und Wiedervorlagen; `datenschutz.zugriff` lässt nur den Inhaber ansehen und niemanden ändern (in `contacts` und `historie`), die Liste zeigt sie mit `?gesperrt=1`. Ort zur PLZ: `contacts/plz.py` liest `contacts/daten/plz.tsv` (PLZ, Gemeinde, Zahl der Straßen; aus OpenPLZ/OpenStreetMap, ODbL – Quellenangabe im Dateikopf und in der README behalten; neu erzeugen mit `werkzeuge/plz_erzeugen.py`), eindeutig ab 90 % der Straßen. `/adressen/orte/?plz=` liefert die Orte; Felder mit `PLZ_ATTRS` (`data-plz`) füllen in `static/js/app.js` das Feld mit `data-ort` aus, nur ohne `data-land` oder bei Deutschland und solange der Ort nicht von Hand geändert wurde.
- `invoicing/` – Rechnungen: Entwurf (frei änderbar) → Festschreiben (`beleg.festschreiben`): vergibt die Nummer (`Rechnung.naechste_nummer`, Jahr zweistellig + vierstelliger Zähler, lückenlos nach den Altbelegen), friert alle Angaben in `Rechnung.beleg` (JSON) ein und legt das PDF unter `<DATA_DIR>/archiv/rechnungen/<jahr>/` ab. PDF/A-3 per Typst (`invoicing/typst/rechnung.typ`, Schriften aus `invoicing/schrift/`, Systemschriften ignoriert), ZUGFeRD-XML (EN 16931) mit drafthorse, GiroCode mit segno, Logo aus `Firmendaten.logo` und Unterschrift aus `Firmendaten.unterschrift` (Bytes in der DB, nicht eingefroren – das abgelegte PDF ist maßgeblich; `beleg.druckbilder` reicht beide und den Briefkopf (`kopf`) an jede Belegart; der Text darunter, `unterschrift_text`, liegt mit den Absenderdaten im Beleg; steht der Name darin, lässt `beleg.schlusstext` die Namenszeile des Grußes beim Drucken weg, der gespeicherte Text bleibt). Den Seitenwechsel in Positionen regelt `leistung` in der Vorlage: bis 60 mm Höhe bleibt die Position ganz, darüber trennt die Seite nur zwischen zwei Zeilen der Beschreibung; was selbst höher ist, muss brechen dürfen, weil ein nicht trennbarer Block sonst über den Seitenrand läuft. Am Ende gilt dasselbe für den Schluss: Schlusstext und Unterschrift bleiben bis 60 mm ganz, darüber trennt die Seite nur zwischen Zeilen, und die Zeilen ab der vorletzten mit Text (Gruß und Name) sind `sticky`; der Zahlungshinweis ist `sticky`, sobald ein Schluss folgt (ohne Schluss nicht, sonst wechselte er allein die Seite). Texte aus dem Browser kommen mit `\r\n`, `beleg.absaetze` trennt nur an `\n\n`: Ein Schlusstext ist dann ein Absatz mit Leerzeilen, deshalb arbeitet der lange Fall mit Zeilen statt Absätzen. Der Zahlungshinweis unter dem Betrag ist fest (`druckdaten`), außer `Firmendaten.zahlungstext` ist gefüllt: dann ersetzt `beleg.zahlungshinweis` die Zeilen Zahlungsziel, Bankverbindung und Verwendungszweck (Platzhalter `ZAHLUNG_PLATZHALTER`, unbekannte lehnt `FirmendatenForm.clean_zahlungstext` ab; eingefroren als `beleg["zahlungstext"]`, Storno, Korrektur und Mahnung ignorieren ihn). Einheit leer heißt „ohne“ (`invoicing.views.EINHEITEN`, Artikel-Auswahl „ohne Einheit“, Import „ohne“/„-“): gedruckt wird nur die Zahl, im XML C62. Steuerfälle (`Rechnung.Steuerfall`): § 19, Regel, § 13b und steuerfrei (§ 4). `Firmendaten.umsatzsteuer` ist eine Auswahl, deren Werte zugleich Steuerfälle sind, und belegt neue Rechnungen, Angebote und Auftragsbestätigungen vor; `firma.kleinunternehmer` ist eine Property daraus (bis 0.36 ein Feld, Migration `core.0008`) und schaltet die Umsatzgrenzen ein. Steuerfrei: Hinweis aus `Firmendaten.steuerfrei_hinweis` über `invoicing.models.steuerhinweis`, ohne ihn fehlt eine Pflichtangabe (`hinweis_fehlt`, auch bei Angebot und Auftragsbestätigung, nicht bei der Korrektur); `beleg.beleg_steuerhinweis` gibt Storno und Korrektur den eingefrorenen Hinweis des Originals; im XML Kategorie E mit dem Hinweis als BT-120, ohne VATEX-Code; `core.umsatz` zählt steuerfreie Rechnungen nicht (§ 19 Abs. 2 UStG); DATEV 8100/4100. Vorschau und Ansicht zeigen die PDF-Seiten als PNG (pypdfium2, `beleg.seitenbilder`), nie per iframe: der PDF-Betrachter mancher Browser bleibt dort schwarz. Danach sperren `save()`/`delete()` jede Änderung außer den Versandfeldern. Korrektur nur per Stornorechnung (`beleg.stornieren`): eine eigene, sofort festgeschriebene Rechnung mit `storno_zu` aufs Original, negativen Mengen (EN 16931 verbietet negative Einzelpreise) und BT-25/26 im XML; „storniert“ wird aus dieser Verknüpfung abgeleitet, das Original bleibt unberührt. Teilbeträge mindert eine Rechnungskorrektur (`beleg.korrektur_anlegen`, `Rechnung.korrektur_zu`, mehrere je Rechnung): ein Entwurf mit den Positionen des Originals in negativer Menge, Empfänger und Steuerfall gesperrt, nur negative Mengen und höchstens bis `Rechnung.korrigierter_betrag`; im XML wie die Stornorechnung mit BT-25/26. Nach einer festgeschriebenen Korrektur ist kein Storno mehr möglich, nur weitere Korrekturen. `Rechnung.kopieren()` legt einen neuen Entwurf mit denselben Angaben an. Ein Entwurf, der vor heute zuletzt gespeichert wurde (`geaendert`) und auf einen früheren Tag datiert ist, zeigt im Editor das heutige Datum mit dem alten als Hinweis am Feld (`invoicing.forms.datum_auf_heute`, nur bei GET, auch für Angebot und Auftragsbestätigung); gespeichert wird es erst mit dem Formular. XRechnung 3.0 (CII) für Adressen mit `Kontakt.xrechnung`: dieselbe XML steckt im PDF (Profil XRECHNUNG) und liegt als maßgebliches Original daneben (`Rechnung.xml_datei`, `xml_sha256`). Die Käuferreferenz (BT-10) kommt von der Rechnung oder aus der Adresse; ist sie eine Leitweg-ID (`contacts.models.ist_leitweg_id`, Prüfziffer MOD 97-10), ist sie zugleich die elektronische Adresse des Käufers (Schema 0204). Zusätzliche Pflichtangaben in `Rechnung._fehlt_fuer_xrechnung`. Versand per SMTP mit den Zugangsdaten aus `Firmendaten` (`versand.py`, hängt `beleg.anhaenge` an, auch für Angebote). Live-Rechnen und Pflichtangaben-Anzeige laufen zusätzlich in `static/js/app.js` (`[data-invoice]`, für Angebote mit `data-beleg="angebot"`); maßgeblich ist die Prüfung auf dem Server (`Rechnung.fehlende_angaben`). Was jede Belegart braucht, liegt einzeln in `invoicing/beleg.py` (`absender_daten`, `empfaenger_daten`, `positionen_daten`, `briefkopf`, `druck_positionen`, `druck_summen`, `setzen`) und `invoicing.models.summen`; die Positionszeile des Editors ist `invoicing/position.html`, der Umschalter Rechnungen/Angebote `invoicing/belegarten.html`.
- Briefkopf (Spezifikation B-6): Seite `/einstellungen/briefkopf/` (`core:briefkopf`, nur Inhaber, `BriefkopfForm`; Logo und Marke liegen seit 0.39 dort, nicht mehr im `FirmendatenForm`) mit Vorschau aus `beleg.kopf_vorschau` (echte Rechnungsvorlage ohne Inhalt, als PNG oben abgeschnitten). Felder in `Firmendaten` (`kopf_art`, `logo_lage`, `logo_hoehe` in `LOGO_MM`, `logo_zuschneiden`, `kopf_name`, `kopf_anschrift`, `kopf_linie`, `akzentfarbe`, `kopfbild`, `kopfbild_breite`); die Vorgaben ergeben pixelgleich den Kopf bis 0.38. `beleg.kopf_einstellungen` macht daraus das Wörterbuch für die Vorlage, `beleg.druckbilder` schneidet auf Wunsch den Rand des Logos ab (`zuschneiden`, nur beim Drucken) und lässt es bei einem Kopfbild weg, `kopf_druck` setzt `logo`, `kopfbild` und `briefkopf` in die Druckdaten jeder Belegart. Gesetzt wird der Kopf in `invoicing/typst/kopf.typ` (`briefkopf`, `abstand-zum-inhalt`: Inhalt 64 mm unter dem Kopf, nie vor 94 mm unter der Blattkante); ohne `briefkopf` entsteht der bisherige Kopf. Der Auskunftsbrief lädt dieselbe Datei, deshalb kompiliert `contacts.datenschutz.setzen` mit `root=beleg.WURZEL`. Grenzen: Kopfbild endet spätestens 44 mm unter der Blattkante, Logo höchstens 20 mm hoch; `tests/test_briefkopf.py` prüft auf der Vorschau, dass der Streifen über dem Infoblock frei bleibt.
- `angebote/` – Angebote (Spezifikation B-2): Entwurf → Fertigstellen (`beleg.fertigstellen`): Nummer aus eigenem Nummernkreis (`Angebot.naechste_nummer`, Format wie die Rechnung, nach den Altbelegen der Art Angebot), Angaben eingefroren in `Angebot.beleg`, PDF/A-3 mit derselben Typst-Vorlage ohne ZUGFeRD unter `<DATA_DIR>/archiv/angebote/<jahr>/`. Danach gesperrt wie die Rechnung, änderbar sind nur Versand, Antwort des Kunden (`antwort`, `antwort_am`) und `rechnung`; eine geänderte Fassung ist eine Kopie (`Angebot.kopieren`). Gültigkeit in Tagen (`bindefrist`), „abgelaufen“ und der Stand für die Anzeige (`Angebot.stand`) werden abgeleitet. `beleg.rechnung_erstellen` macht aus dem Angebot einen Rechnungsentwurf mit Empfänger, Steuerfall, Betreff und Positionen, Kopftext mit Bezug aufs Angebot; `Angebot.rechnung` (OneToOne, `SET_NULL` beim Löschen des Entwurfs) verhindert eine zweite Rechnung. Offene Angebote stehen auf der Übersicht, Entwürfe aller Belegarten in ihrer rechten Spalte (`core.views._entwuerfe`).
- `auftraege/` – Auftragsbestätigungen (Spezifikation B-2), Seiten unter `/auftragsbestaetigungen/`, aufgebaut wie `angebote/`: Entwurf → Fertigstellen (`beleg.fertigstellen`, eigener Nummernkreis `Auftragsbestaetigung.naechste_nummer` ohne Altbelege, PDF/A-3 unter `<DATA_DIR>/archiv/auftraege/<jahr>/`), danach gesperrt bis auf Versand und `rechnung`. Optional Ausführung (`leistung_von`/`leistung_bis`), die `beleg.rechnung_erstellen` als Leistungszeitraum in den Rechnungsentwurf übernimmt. `beleg.aus_angebot` macht aus einem Angebot einen Entwurf (`Auftragsbestaetigung.angebot`, OneToOne, vermerkt die Zusage); gibt es ihn, führt „Rechnung erstellen“ am Angebot zur Auftragsbestätigung, und die Zusage lässt sich nicht zurücknehmen. Im Editor `data-beleg="auftrag"`.
- `artikel/` – Artikel und Leistungen (Spezifikation B-1): Nummer A-0001 fortlaufend, Einheit aus `invoicing.beleg.EINHEIT_CODE`, Einzelpreis netto, „inaktiv“ statt Löschen. - `importe/` – Import von Adressen und Artikeln (Spezifikation M-6), Seiten unter `/import/` (Links „Importieren“ in beiden Listen). `lesen.lesen` macht aus CSV (UTF-8, UTF-16 oder Windows-1252, Trennzeichen aus der ersten Zeile), XLSX (openpyxl, nur lesend) und ODS (selbst gelesen) Spaltentitel und Zeilen als Text mit der Zeilennummer der Datei; Grenzen 10 MB, entpackt 100 MB, 10.000 Zeilen, 100 Spalten; XML mit Dokumenttyp-Definition lehnt es ab (expat wie in `eingang/lesen.py`). `Import` hält die Tabelle zwischen Hochladen und Übernahme, nur für den Benutzer, der sie hochgeladen hat; gelöscht nach Übernahme oder Abbruch, liegen gebliebene nach einem Tag beim nächsten Hochladen (`Import.aufraeumen`). `vorlagen.py` (Docstring): Felder je Ziel, eingebaute Vorlagen (Kontorfreund-Exporte, Lexware Office, Google Kontakte), übliche Spaltennamen und gespeicherte `Zuordnung`en; `vorschlagen` nimmt eine Vorlage ab 60 % Treffern. `uebernahme.pruefen` ist der Probelauf: jede Zeile durch `KontaktForm` bzw. `ArtikelForm`, Dubletten wie `contacts.views.moegliche_dubletten`, Nummern aus der Datei, wenn sie frei sind; `uebernehmen` speichert dasselbe in einer Transaktion. Ändern sich Felder oder Regeln von Adresse oder Artikel, gehören `FELDER` und die Umsetzung in `uebernahme.py` angepasst, neue Exportspalten auch in die Vorlage „Kontorfreund“.
- Sicherheit: `docs/sicherheit.md` ist die Prüfliste nach OWASP ASVS 5.0 Stufe 2 mit den dokumentierten Sicherheitsentscheidungen; bei Änderungen an Anmeldung, Rechten, Dateien, Verbindungen oder Protokollen nachführen. `core/sicherheit.py`: nur GET, HEAD und POST (`methoden`), `Cache-Control: no-store` für alles außer statischen Dateien (`nicht_speichern`), 403 und abgelehnte CSRF-Prüfungen als Aktion `verweigert` ins Protokoll (`handler403`, `CSRF_FAILURE_VIEW`). Das Fehlerprotokoll formatiert `config/fehlerprotokoll.py` (Zeit mit UTC-Abstand).
- `protokoll/` – Änderungsprotokoll (Spezifikation K-6), Seite `/protokoll/` nur für Inhaber. Signale an den Modellen in `erfassen.ERFASST` schreiben bei Anlage, Änderung und Löschung einen `Eintrag` mit Feld, altem und neuem Wert als Text (editierbare Felder ohne JSON; Kennwörter als „•••“, `last_login` nie). Neue Modelle mit Geschäftsdaten gehören in diese Liste. Wer es war, liest `eintragen` aus der Anfrage, die `middleware.anfrage_merken` in einer ContextVar hält. Positionen von Rechnung und Angebot protokollieren die Editoren als Ganzes (`positionen_geaendert`), weil sie beim Speichern alle neu entstehen. `Eintrag` lässt sich nur anlegen: `save()` auf Bestehendes, `delete()` und `update()`/`delete()` am QuerySet werfen `Unveraenderbar`. Einzige Ausnahme ist `Eintrag.schwaerzen` nach einer Löschung auf Verlangen (Art. 17 DSGVO) oder nach Ablauf der Aufbewahrungsfrist: Bezeichnung und Werte weg, Zeitpunkt, Benutzer und Aktion bleiben. Bewusst ohne Datenbank-Trigger, weil Tests mit `transaction=True` die Datenbank am Ende leeren.
- Tests setzen `DATA_DIR` automatisch auf einen Temp-Ordner (`tests/conftest.py`), damit keine Sicherung den echten Datenordner berührt; die tägliche Prüfung der Ablage (`pruefung.bei_bedarf`) ist dort abgeschaltet. Die Fixture `client` ist dort als Inhaber angemeldet; Tests der Anmeldung nehmen `anonym`.
- Jeder weitere Fachbereich bekommt eine eigene App (z. B. `exports`).
- Oberfläche: Django-Templates (`templates/base.html` + App-Templates, Django-6-Partials), eigenes CSS in `static/css/app.css` mit Design-Tokens, kein JS-Framework. Gestaltungsregeln: `PRODUCT.md`, `.impeccable/surfaces/`.
